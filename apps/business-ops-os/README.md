# Business Ops OS

Elevate Education's operations module (`@elevate/business-ops-os`, Next.js, basePath `/ops`, port 3003). It runs admissions: leads, demo students and their classes, applications with a password-confirmed final approval that gives the admission number, active and past students (KYC, onboarding, exits, readmission), guardians, counselling, parent-teacher meetings, events and webinars, teachers (directory, profile with Academic activity, and the student reviews teachers write in Academic OS), annual fee agreements and manual fee records, progress reports, the staff task tracker (tasks with acknowledgement, review, dependencies and work updates), end-of-day reports with versions and a manager inbox, the import of the old task tracker's backups, one search box, the Marketing lead handoff, the enrolment handoff to Academic OS, and the admissions reports. It is also steward of `core.staff_members`, `core.departments` and the canonical student `core.students` (D-033). Student flow: **lead → counselling → demo (3 demo days, D-038) → application (form, signatures) → final confirmation (number, D-040/D-041) → enrolment in Academic OS**. The student's identity is created at demo booking and reused from then on.

**HR and Operations were removed by the owner on 20 Oct 2026 (D-032):** employee records, recruitment, onboarding/offboarding, staff attendance, shifts, leave, compensation, assets, tasks, escalations, SOPs, the policies register, incidents, decisions, risks, projects, milestones, responsibilities, the work inventory and the operations/HR reports, with their tables (migration `0002_remove_hr_operations`), permissions, roles and seeds. Everything is recoverable from git: the last commit that contains it is `63da4e4` (branch `feature/business-ops-hr-admissions`), e.g. `git checkout 63da4e4 -- apps/business-ops-os/src/server/hr`.

Status (D-013): services and domain rules are **Tested** where a test is named in `requirements/REQUIREMENTS.md`; screens are **Implemented** (redesigned 21 Oct 2026 and looked at in a browser by the build agents, but no automated browser test); nothing is Deployed. Migrations `0000`–`0008` exist and are applied to the owner's local database only (`0007_admissions_lifecycle`, `0008_staff_tasks`). `0009_academic_teacher_workspace_tasks` (task events, updates, dependencies, EOD versions and review events, import batches, review acknowledgements) is generated and **not applied**; the owner runs `npm run db:migrate`. Test count and whole-suite result: see `IMPLEMENTATION_STATUS.md`.

## Integration
- Produces `ops.admission.enrolment_requested` v1 (with `existingStudentId` when known, `coreStudentId` = the admission's core student and `academicYear` from the application — IR-OPS-STU-2 done); consumes `academic.enrolment.confirmed` / `.rejected` v1 (`ops.enrolment-replies`) and `marketing.lead.handed_off` v1 (`ops.lead-intake`, producer not built: IR-MKT-OPS-HANDOFF).
- Reads `GET /academic/api/internal/v1/summary`, `GET /academic/api/internal/v1/students/{id}/summary` (`AcademicStudentSummaryV1`, IR-OPS-STU-1 done), `/reviews` (D-058), `/teachers/{staffId}/activity` and `/demo-attendance` (D-060), and `GET /marketing/api/internal/v1/summary`. Serves `GET /ops/api/internal/v1/demo-sessions?date=` to Academic only (R5). Each Academic read fails to "source unavailable", never to zero; for a demo class Ops knows is linked, counsellor marking and the move to demo attended wait while Academic is unreachable (D-066).
- Open: `ops.enrolment.closed` v1 so Academic stops attendance after an exit (IR-OPS-EXIT-1); Academic batch end dates (IR-OPS-EXIT-2).
- Jobs, run by hand until a scheduler exists (IR-OPS-02, IR-OPS-PLT-2): follow-up reminders, enrolment replies, lead intake, and `demo-academic-marks` (re-reads Academic's marks for open demos).
- Open requests to other owners: `docs/INTEGRATION_REQUESTS.md`.
